# Friction encountered when using Arkiv

Honest record of what hindered or surprised while building Safe Whistle over the `@arkiv-network/sdk` 1.0.0 SDK and the Rabdi testnet. Each item states **how it was discovered**, **the impact** and **what we did**. Measured items have their source in `validation/RESULTS.md`.

## 1. Maximum lifetime of an entity (discovered by error)
- **What happened:** requesting 365 days of retention was refused by the chain: *"the expiry resolves to block …, more than the chain's maximum lifetime of 7884000 blocks"*. The ceiling is **7,884,000 blocks, ~182.5 days**.
- **How we found out:** integration test on the local node. The value **was not re-confirmed on Rabdi** (probably it is the same parameter).
- **Impact:** without renewal the tip disappears. This became a requirement (RN-06).
- **What we did:** the store refuses retention above the ceiling minus 1 hour of slack; default retention of 150 days; a relayer job renews what expires within 60 days.
- **Suggestion:** expose the limit (in blocks) through an SDK call, instead of only in the error message.

## 2. Maximum content size (limit without cause message)
- **Measured on Rabdi:** up to **128,960 bytes** (~126 KiB) are accepted. **131,072 bytes (exactly 128 KiB)** were **refused by the network without an informed cause**, and 131,073 bytes were refused by the SDK itself.
- **Impact:** the useful limit is smaller than the "128 KiB" one imagines, and the refusal at 131,072 does not explain the reason.
- **What we did:** parts of 120 KiB (`PART_PAYLOAD_BYTES`) and reassembly; large attachments become several entities grouped by `contentHash`.
- **Suggestion:** document the useful limit and return the cause of the refusal.

## 3. Query requires at least one filter; maximum page of 100
- **What happened:** `select` without a filter is refused. The maximum page is 100.
- **Impact:** to list "everything" you need an indexed attribute as a filter and paginate.
- **What we did:** every record carries an indexed `newsroom`; the store paginates in blocks of 100.

## 4. Fixed schema in the client: new column and optional column
- **What happened (twice, when adding `authorName` to `anotacao` and `resposta`):**
  1. *"the create names a column this schema does not have"*, because the schema declared in the code did not have the column.
  2. After declaring it, *"the create leaves out a required str column. Give it a value, or declare it str().optional()"*, because every column is mandatory, unless it is declared `.optional()` or with a default value.
- **How we found out:** only the **integration test against the real node** caught it. The tests with the in-memory stand-in passed.
- **Impact:** a schema change needs to be thought through together with the records already written.
- **What we did:** `authorName` declared as `str().optional()`. We treat an empty or null value on read as "no author" as a precaution; **we did not confirm which of the two the node returns**.
- **Not verified:** what happens, on Rabdi, when writing with a schema that gained a column after records of the old schema already exist. There are already old Rabdi records (without `authorName`) that are read normally.

## 5. The access key goes in the RPC URL path
- **What happened:** `rabdi({ accessKey })` builds the RPC as `https://rpc.rabdi…/<key>`. Without a key, the SDK warns and uses the public endpoint, with a strict rate limit.
- **Impact:** in a browser app, the access key would be exposed in the code or in the user's wallet configuration.
- **What we did:** the key never enters the browser code. In the newsroom panel it is optional, typed by the user; the source screen read uses the public endpoint.
- **Suggestion:** accept the key in a header, or offer read keys with limited scope.

## 6. No warning when an entity expires
- **What happened:** the entity simply **disappears from queries**, with no event. Measured on Rabdi with 30 s lifetime.
- **Impact:** whoever does not renew loses the data without noticing.
- **What we did:** the relayer renews periodically and the newsroom screen lists what expires soon.

## 7. Permission semantics that had to be measured
- **Measured (local node and Rabdi):** after `changeOwnership`, the creator **does not** delete or extend, unless the entity has `permissionlessExtension`, and **never** changes the content of a `readonly` entity. `$creator` remains the original creator.
- **Impact:** it is exactly what the custody model needed, but it only became clear after testing each combination.
- **What we did:** we created with `readonly` and `permissionlessExtension`, and transferred ownership. Any account can extend (the cost is borne by whoever extends), and the relayer cannot delete.

## 8. SDK heavily typed per schema
- **What happened:** access by entity type (tip, reply, note) is dynamic, and the type generated by the schema got in the way.
- **What we did:** a narrow interface (`SdkPublic`/`SdkWallet`) and a backend with the same contract suite for the in-memory stand-in and for the real SDK.

## 9. What worked without friction
- **Browser wallet:** `createWalletClient({ account: <address>, transport: custom(EIP-1193 provider) })` signed create, read, extend and change ownership **without an adapter** (test with fake provider, `validation/B0-RESULT.md`). Real MetaMask has not yet been tested.
- **Cost:** ~0.00017 tGLM per small tip on Rabdi.
- **Local development node** (`arkiv-reth-dev`) with 2 s blocks behaved like Rabdi.
